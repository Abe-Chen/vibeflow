# 需求文档：多模型并行出方案与探索池

## 1. 需求名称

vibeflow 多模型并行出方案 + 探索池（plan --multi / consult / synthesize / accept-plan / 路径互通）

## 2. 需求背景

当前 vibeflow 的 plan 阶段只由单个模型（默认 codex）产出一份方案 `01_plan_v1.md`，多模型协作仅体现在 plan-review 阶段由不同模型评审挑错。这意味着：

- 用户在复杂需求上只能拿到单一视角的方案，方案有偏时只能在同一思路上反复打补丁，无法获得真正不同方向的备选；
- 「多个模型各出一套方案，再对比 / 咨询 / 融合 / 择优」是 vibeflow 在 PRD §7.2 中已规划、且差异化最强的能力，但尚未实现；
- PRD §7.2 已完成构想层面的重写（探索池可选、路径互通、主动引导菜单、用户主导决策不依赖自动 Judge），本次需求是将该构想落为可据以编码的设计方案。

**本任务的交付物是设计文档，不是代码。** 流程为 requirement → plan → plan-review → finalize，锁定后用 deliver 交付设计文档；develop（代码实现）留待后续单独任务进行。

## 3. 目标用户和场景

**目标用户**：使用 vibeflow 编排多模型 AI 研发流程的开发者（Vibe Coding / AI Coding 用户），已配置 2 个及以上模型 CLI。

**核心场景**：

| 场景 | 描述 | 对应路径 |
|---|---|---|
| 复杂需求多视角出方案 | 需求复杂或方向不确定，用户想让 2~3 个模型各自独立出一套方案再对比 | `plan --multi` → 菜单选择 |
| 直接择优 | 多套方案中有明显更好的一套，直接选定进入评审 | `accept-plan` → plan-review |
| 咨询深挖 | 对某套方案有疑虑，想听另一个模型的单轮看法 | `consult` |
| 融合成版 | 各方案均有可取之处，让某模型按用户偏好融合为一版 | `synthesize` → `accept-plan` |
| 评审后反悔 | plan-review 发现方向有偏，锁定前退回探索池继续融合 | 退回探索 → 再 accept → 再评审 |
| 简单需求不受影响 | 简单需求仍走现有单模型单方案路径，零感知变化 | 现有 standard_feature |
| 复盘回看 | 任务结束后回看探索池全过程（谁出的方案、咨询了什么、怎么融合的） | explore/ 目录产物 |

## 4. 核心需求列表

### P0（本期设计必须覆盖）

| # | 需求 | 说明 |
|---|---|---|
| 1 | **plan --multi 多模型并行出方案** | 2~3 个模型并行各出一套方案，产物分别落任务目录下 `explore/`（如 01_plan_A.md / 01_plan_B.md / 01_plan_C.md），每份产物标注出自哪个模型 |
| 2 | **accept-plan 选定方案** | 从探索池中选定一份（原始方案或融合稿），复制为正式产物 `01_plan_v1.md`，衔接既有 plan-review → finalize 流程；锁定前可重新执行覆盖前次选择 |
| 3 | **决策菜单 + next 兜底** | plan --multi 完成后主动展示可选动作菜单（accept 某方案 / 咨询 / 融合 / 重跑换模型 / 改需求）；`vibeflow next` 能感知探索池状态并给出引导，避免用户迷路 |
| 4 | **路径互通（锁定前）** | finalize 锁定前，单方案 / 多方案 / 探索池可自由切换，含从 plan-review 退回探索池；锁定后变更一律走既有 change-request |
| 5 | **对 standard_feature 零破坏** | 不加 --multi 时行为与现状完全一致；探索池是可选叠加，不改变现有单方案路径的任何产物、状态与命令语义 |

### P1（本期设计应覆盖）

| # | 需求 | 说明 |
|---|---|---|
| 6 | **consult 单轮咨询** | 就某个方案，指定上下文文件，单轮咨询指定模型的看法；产物落 explore/ |
| 7 | **synthesize 方案融合** | 指定若干份输入方案，让指定模型融合为一版，可附带用户偏好；产物落 explore/ |
| 8 | **探索全程可追溯** | explore/ 下所有产物（各模型方案、咨询记录、融合稿）永久保留，accept 选择历史可查，复盘能看到全过程 |
| 9 | **与既有命令兼容** | 与 --force（阶段重跑及级联重置）、next（导航）、deliver（交付）、change-request（锁定后变更）的行为衔接均需在设计中明确 |

### P2（本期设计预留，不强制展开）

| # | 需求 | 说明 |
|---|---|---|
| 10 | **自动 Judge 预留位** | 「让某模型自动裁决哪个方案更好」本期不做，但设计上预留扩展位置，说明未来如何挂入 |
| 11 | **探索池增强命令预留** | PRD §15.3 提及的 plan --multi-extend（单方案纳入探索池）、plan --add（追加模型）、plan-status（探索池可视化）等，本期是否纳入设计见「阻断性决策」 |

## 5. 范围（本期做什么）

1. 产出一份**可据以编码的设计方案文档**，必须覆盖：
   - 新命令清单与参数定义（plan --multi、consult、synthesize、accept-plan，及确认纳入的其他命令）；
   - `explore/` 目录结构与产物命名规则；
   - run.json 需要的扩展字段（探索池状态、方案清单、accept 历史等）；
   - 各新命令与现有阶段 / 状态机（plan → plan-review → finalize）的衔接点，含「锁定前路径互通、锁定后走 change-request」的边界定义；
   - 对 standard_feature 单方案路径的零破坏保证方式；
   - 决策菜单与 `vibeflow next` 的引导内容设计；
   - 分步实现建议（供后续 develop 任务拆分）。
2. 设计走完本任务的 requirement → plan → plan-review → finalize 流程，锁定后 deliver 交付。

## 6. 不做范围（本期明确不做）

1. **不写代码**——develop 阶段留待后续单独任务，由人工把控落盘（改动对象是 vibeflow 自身核心）。
2. **不做自动 Judge / 自动裁决**——本期一切选择、融合决策由人主导，自动裁决仅在设计中预留位置。
3. **不强制多模型路径**——不把探索池设为默认或必经路径，不修改 standard_feature 的默认行为。
4. **不另起一套机制**——不为探索池新建独立于 run.json 状态机、adapter 层、context builder 之外的并行体系（设计须基于复用，复用不可行处需在设计文档中说明理由）。
5. **不做锁定后的探索池回退**——finalize 锁定后不允许 back 回探索池，统一走既有 change-request。
6. **不做 GUI / 可视化界面**——仅 CLI 文本菜单与命令。

## 7. 验收标准

本期交付物为设计文档，验收以文档质量与流程闭环为准：

1. 设计文档完整覆盖「范围」中列出的 7 项内容，每个新命令均有：命令名、参数、前置条件、产物路径与命名、对 run.json 的读写、失败时的状态处理。
2. 能从文档直接回答以下场景题，无歧义：
   - 用户跑了 `plan --multi` 出 3 套方案后，next 提示什么？菜单有哪些选项？
   - 用户 consult 两轮、synthesize 一版后 accept，正式 `01_plan_v1.md` 来自哪份文件？explore/ 里留下哪些产物？
   - plan-review 给出否定意见，用户想退回探索池重新融合，执行什么命令？run.json 状态如何变化？
   - finalize 锁定后用户想改方案，系统如何拦截并引导到 change-request？
   - 不加 --multi 的老用户，所有现有命令行为有无任何变化？（答案必须是「无」，且文档说明保证方式。）
   - `--force` 重跑 plan 阶段时，已有 explore/ 产物如何处理？
3. run.json 扩展字段有明确清单与含义，且声明对旧任务（无这些字段的存量 run.json）向后兼容。
4. 分步实现建议把后续 develop 拆为可独立验证的步骤，每步标注涉及的现有模块（状态机 / adapter / context builder / next-advisor 等）。
5. 设计文档通过 plan-review 跨模型评审并完成 finalize 锁定，最终经 deliver 交付。

## 8. 需要人工确认的问题

### 阻断性决策（不拍板则方案方向无法确定）

1. **增强命令的本期设计范围**：核心要求只明确了 plan --multi / consult / synthesize / accept-plan / 退回探索 五件事；PRD §15.3 还列了 `plan --multi-extend`（单方案中途转多方案）、`plan --add <model>`（追加模型出方案）、`plan-status`（探索池可视化）。这三条是纳入本期设计、还是仅作 P2 预留？——其中 multi-extend 直接影响「单方案 ↔ 多方案自由切换」的实现深度（不做它，单方案转多方案只能重跑 plan --multi）。
2. **退回探索的命令形态**：从 plan-review 退回探索池，是新增独立命令（如 PRD 中的 `back-to-explore`），还是复用既有 `--force` 重跑机制的语义扩展？两者对状态机的设计方向不同，需先拍板。
3. **plan --multi 的副作用确认粒度**：产品红线要求「调用外部 CLI 默认每步 [Y/n] 询问」。一次 --multi 会连续调用 2~3 个模型 CLI，是一次确认即跑全部模型，还是逐模型确认？以及 `-y` 自动链模式下，--multi 跑完后是否必须停在决策菜单等人（探索池天然人主导，建议必须停）？这决定交互骨架。

### 可延后项（plan / finalize 阶段先给方案再确认）

1. 并行的执行方式：真并发调用多个模型 CLI，还是顺序执行逐个出方案（影响等待时长与实现复杂度，不影响产物与流程）。
2. 默认模型组合与数量：--multi 不带 --models 时默认用哪 2~3 个模型、从何处读取配置。
3. 部分失败语义：3 个模型中 1 个失败时，阶段算成功（带告警，可补跑）还是失败（整体重跑）。
4. explore/ 产物的具体命名规则：方案后缀用 A/B/C 还是模型名；consult / synthesize 产物的编号与命名格式；同名重跑时的覆盖 / 追加策略。
5. accept 历史与探索元数据记在 run.json 还是 explore/ 内的清单文件。
6. deliver 交付时是否携带 explore/ 探索产物（全量带 / 仅带被 accept 链路 / 不带）。
7. consult / synthesize 可指定的模型范围：是否允许使用未参与出方案的其他已配置模型。
8. 决策菜单的具体文案、选项排序（PRD 建议首选项默认是 accept 而非继续探索，防拖延）与退出方式。
